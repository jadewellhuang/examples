# 維護協議（maintenance.md）

這套制度檔由未來的 session（可能是較小的模型）維護。本檔規定怎麼改才不會把制度改壞。

## 0. 改任何檔案前的固定動作

1. 先讀完要改的檔案全文（不是只讀要改的段落）。
2. 留備份：`cp <檔案> <檔案>.bak-YYYYMMDD` 放在同目錄，commit 時一併提交（下一個 session 精簡時可刪超過 60 天的 .bak）。
3. 改完跑一次自查：改動後的句子是否仍然「具體、可執行、有判準」？出現「保持高品質」「注意品質」這類不可執行句就重寫。
4. commit message 寫明「改了哪條規則＋為什麼」，不能只寫 "update rules"。

## 1. 權限分級：哪些可以自己改、哪些要先問使用者

**可以自己改（不用問）**：
- `.claude/memory/lessons.md`：新增條目（這是設計上鼓勵的，見第 2 節）。
- 各規則檔的**事實修正**：路徑改了、工具名改了、環境行為變了——前提是新事實經過實測或官方文件查證，並在改動處註記日期與依據。
- 錯字、格式、失效連結。

**要先問使用者（用 AskUserQuestion，工具不存在就在回覆中列選項提問，附建議）**：
- 刪除或放寬任何**硬規則**（例如「重試上限兩輪」「驗證不自驗」「回報三態」）。放寬規則通常是當下嫌麻煩，而規則存在正是為了擋住「當下嫌麻煩」。
- 改 CLAUDE.md 的「每個 session 都適用的五條」。
- 新增會拉高每 session 固定成本的東西（例如把大檔改成 @import）。
- 刪除整個規則檔或 agent 定義。

**絕對不改**：把驗收條件改寬鬆來讓自己的產出過關（judgment.md 第 4 節列為最危險訊號）。

## 2. 踩坑回寫：lessons.md 的格式與時機

**時機**：(a) 被使用者糾正；(b) 自己發現環境行為與預期不符（工具參數、proxy、依賴）；(c) verifier 抓到你以為對的錯。三者任一發生，**當場寫**，寫完再繼續原任務——「等收尾再寫」的教訓九成會消失。

**格式**（新條目加在檔案最上面）：

```
## YYYY-MM-DD ｜ {一句話標題}
- 情境：當時在做什麼
- 錯誤：做了什麼、為什麼錯（或：什麼環境行為出乎意料）
- 正解：下次直接怎麼做
- 適用範圍：{總是 / 只在某情境}
```

每條 ≤6 行。寫「下次可直接執行的正解」，不要寫檢討文。

**升級機制**：同一個坑在 lessons.md 出現第二次（代表光記錄擋不住），把正解升格為規則——寫進對應規則檔（照本檔第 0、1 節流程），lessons 條目尾註「已升格至 {檔案} 第 N 節」。

## 3. 精簡（防止制度長成沒人讀的大部頭）

- **lessons.md 超過 40 條**：合併同類、刪已升格與已過時（環境已改）的條目，目標砍回 25 條以內。刪前備份（第 0 節）。
- **任何規則檔超過 150 行**：先刪重複與過時，仍超過就拆檔並更新 CLAUDE.md 路由表。
- **CLAUDE.md 超過 60 行**：立即精簡。它每個 session 都全文載入，是全 repo 最貴的檔案。
- 精簡屬於「要先問使用者」等級**以下**的操作可自行做，但一次 session 只精簡一個檔案，且 commit 單獨提交（方便 revert）。

## 4. 過時偵測

規則檔內的環境事實（工具名、參數、模型代號）如果實測不符：
1. 先確認是真的變了，不是你用錯（派 `claude-code-guide` 查官方文件）。
2. 確認後照第 1 節「事實修正」流程改，並在 lessons.md 記一條。
3. 規則檔之間發現**互相矛盾**：以 CLAUDE.md ＞ delegation.md ＞ 其他 的順序為準，修掉矛盾處，commit message 說明採了哪邊。
