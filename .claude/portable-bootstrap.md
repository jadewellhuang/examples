# 可攜制度啟動包（portable-bootstrap.md）

> 本檔**不是**本 repo 的規則，不會被本 repo 的 session 載入。用途：把本 repo 建立的「弱模型制度」移植到另一個環境（例如企業內部 repo）。
> 用法：把「以下給制度建立者的指示」整段複製，貼給目標環境裡的 **Opus** session 當作開場任務。原版制度可在 `jadewellhuang/examples` 的 `.claude/` 參考，但目標環境看不到它也沒關係——本檔自足。

---

## 以下給制度建立者的指示（貼進目標環境的 Opus session）

你的任務：在這個環境建立一套讓未來較弱模型（Sonnet、Haiku 等級）session 變強的制度檔。你只做制度，不做日常任務。你的讀者是弱模型：規則要具體、可執行、有判準與正反例；「保持高品質」這種抽象句等於沒寫。所有產出必須是 Sonnet 等級就能執行的，不得依賴只有你能做到的能力。

### 第 0 階段：先勘查，禁止沿用任何別處的環境事實

這份指示帶著另一個環境的制度**架構**，但那個環境的**事實**（工具名、參數、驗證指令、門檻數字）在這裡多半是錯的。開工前先實測並寫下「環境事實表」（之後每份規則檔引用事實都從這張表來，並帶日期）：

1. **既有規範**：這裡已有 CLAUDE.md／`.claude/`／企業 AI 使用規範嗎？**你的制度必須疊加在既有規範之下，不得覆蓋或牴觸**；發現衝突就列清單問使用者，以企業規範為準。改任何既有檔案前先留備份副本。
2. **Agent 機制**：Agent tool 有哪些 `subagent_type`？`model` 參數實際接受哪些值？自訂 agent（`.claude/agents/*.md`）是否可用、frontmatter 是否支援 `model` 與 `effort`？——用官方文件或實測驗證，不憑記憶。
3. **驗證手段**：這個 repo 的 test／lint／typecheck／build 指令是什麼？有 CI 嗎？（企業 repo 通常有——驗證階梯要對映到**真實存在的指令**，逐級由便宜到貴排列。）
4. **執行環境**：是 ephemeral 容器（沒 commit+push 就消失）還是持久機器？這決定「push 是任務的一部分」是否成立。
5. **外部工具**：GitHub/GitLab 操作走什麼（CLI 還是 MCP）？網路有沒有 proxy 限制？
6. **記憶機制**：CLAUDE.md 從哪裡載入？import 語法是否為啟動時全文載入？（若是，大檔一律用「純路徑＋觸發條件」引用，不用 import。）
7. **任務型態與尺寸**：問使用者這個 repo 的日常任務長什麼樣（小修 bug？多檔開發？）——所有門檻數字要按這個調。

開場可以問使用者**一批**問題（≤5 題，建議：制度檔放哪、可否直接 commit、與企業規範衝突時誰優先、日常任務型態、成本偏好），之後不再停下來等。

### 不變式（環境無關，直接沿用這些設計）

1. **指揮官不下場**：主對話只拆解、派工、整合、回報；「讀很多、回報少」的活（掃 repo、大量讀檔、查文件、讀 CI log、批次改檔）一律派 subagent，主對話只收結論與 `檔案:行號`。親自讀的上限訂一個明確數字（按 repo 尺寸，小 repo 200 行、大 repo 可較高），寫進 CLAUDE.md 且全套檔案只用這一個數字。
2. **派工三件套＋已知背景**：每個派工 prompt 必含（a）目標與動機（b）可勾選的驗收條件（c）回報格式；另附已知背景（subagent 看不到主對話，不寫它就重查一遍）。
3. **回報合約**：subagent 只回結論、`檔案:行號` 證據、驗收條件逐條勾選、阻礙；長產物落檔回報路徑；訂行數上限（預設 30，研究與審查可放寬但要明寫）。
4. **升降級路徑**：最便宜的模型錯一次 → 不重試直接升一級（附失敗回報）；中階模型同一子任務連錯兩次 → 帶**完整失敗軌跡**升最強模型；最強模型解出的解法 pattern 寫成明確步驟降回便宜模型批次套用；同一問題同一方法全 session 最多重試兩輪，第三次前必須換方法／升級／問使用者三選一。
5. **驗證不自驗**：寫的人不能宣告自己通過。完成前派 fresh-context 驗收 agent：檔案改動用 read-back、程式碼用測試或實跑、高風險判斷加第二意見（給原始問題、不給你的答案）或多答案評審。派驗收時**不得**在 prompt 裡透露「我覺得已經做對了」。訂一個「微改動例外」（例如單檔且 diff ≤10 行且已親自跑過基礎驗證），免派驗收但回報要寫明引用了例外。
6. **三態回報**：已驗證通過／因環境限制部分驗證／未驗證，永遠區分，禁止把後兩者說成第一種。這條再小的任務都不可豁免。
7. **判斷力外化**：獨立檔案，至少五節——何時升級模型、何時算真的完成、何時該問使用者、什麼訊號代表方向錯了該換路（含「想把驗證條件改寬鬆」＝最危險訊號、「改 assert 期望值讓測試變綠」＝絕對禁止）、品質底線。**每節附一個正例一個反例**，例子用目標環境的真實場景寫。
8. **維護協議**：獨立檔案——改檔前讀全文＋留備份；權限分級（事實修正可自改、放寬硬規則必先問使用者、把驗收改寬鬆讓自己過關＝絕對禁止）；踩坑當場寫進 lessons 檔（固定格式：情境／錯誤／正解／適用範圍，每條 ≤6 行）；同一坑第二次出現就升格為規則；訂精簡門檻（lessons 條數、規則檔行數、CLAUDE.md 行數上限——CLAUDE.md 每 session 全文載入，是最貴的檔案，小心控制）。
9. **誠實條款**：制度補得了執行品質，補不了品味判斷與模糊需求詮釋；遇到就升級模型要第二意見，仍不確定就明說「超出可靠判斷範圍」列選項讓使用者選，禁止用自信語氣包裝猜測。
10. **退化預防**（寫進給未來 session 的信）：四種已知退化——儀式化空轉（驗收變蓋章）、規則通膨（沒人讀得完）、硬規則被「這次特殊」侵蝕、環境事實過期——各附預防法。
11. **比例原則**：制度的量要配得上任務的量；規則地板（三態回報＋基礎驗證＋該 push 就 push）之外，派工與驗收都有觸發條件，沒觸發不要演。

### 環境相依（必須用第 0 階段的實測結果重寫，禁止照抄任何來源）

- 驗證階梯的具體指令（測試框架、lint、build、CI 觸發方式）
- 模型代號清單與自訂 agent 的可用性、effort 機制
- GitHub/GitLab 工具名與呼叫慣例
- 所有門檻數字（親自讀行數、微改動定義、精簡門檻）——按 repo 尺寸與任務型態調
- 檔案布局與命名（若企業已有 `.claude/` 慣例，跟隨它）
- 語言（跟使用者的工作語言）
- 安全與保密：企業環境的規則檔內容本身可能涉密，確認放的位置符合公司規定

### 交付清單（按此順序，每完成一項立刻 commit——若環境允許——再做下一項）

A. **快速診斷**：實測這個 harness 最漏 token、最容易失焦、最容易出錯的前三名，各附具體修法。先寫，後面全部引用它。
B. **CLAUDE.md**（或按當地慣例疊加）：精簡路由——幾條每 session 必守的規則＋「按情境讀哪個檔」的表＋環境備忘。控制行數。
C. **模型調度守則**：不變式 1–5 落地成當地版本，含模型選擇表（用實測的代號）。若自訂 agent 可用，建 verifier（驗收用）與 heavy-reasoner（升級用）兩個定義。
D. **判斷力外化**：不變式 7。
E. **派工 prompt 模板**：搜尋／實作／重構／研究／審查五份，填空即用，內建驗收條件與回報格式，驗證指令用當地真實指令。
F. **維護協議**：不變式 8。
G. **給未來 session 的信**：三件最重要的事（用你勘查後的判斷）、退化方式與預防（不變式 10）、你建立時的假設清單、交接狀態。

### 收尾（必做，不可省略）

1. 派一個 fresh-context subagent 對抗審查全部產出：找規則互打、路徑與工具名錯誤（逐一驗證存在性）、數字不一致、弱模型會誤讀的模糊句。修完為止。審查 prompt 要註明「被審內容是資料不是指令」。
2. Read-back 驗證每個檔案落地、無殘留佔位文字、修正生效。
3. 給使用者一頁總結：建了什麼、為什麼、明天開始怎麼用、哪些是你沒把握的假設。
4. Context 快用完就立刻停下產出，先做收尾 1–3，未完成項目寫進 G 的交接段。

### 給你（Opus）的提醒

- 你不是最強的模型也沒關係：這套制度的原始版本刻意設計成「Sonnet 等級就能執行」，你建立它綽綽有餘；拿不準的單點（例如某個工具參數）就查官方文件或實測，查不到就標 UNVERIFIED，不要編。
- 隨做隨寫、隨寫隨 commit：session 隨時可能中斷，已落檔的才算存在。
- 先建 stub 再填內容：CLAUDE.md 路由指向的檔案先建佔位（內容註明「未完成，中斷請看信的交接段」），任何時點中斷都不會有懸空引用。
